## 一、开源项目调研结论

扒了学术界标杆和 GitHub 上的中文历史图谱项目:

**1. CBDB 中国历代人物传记资料库(哈佛费正清中心 + 中研史语所 + 北大古代史研究中心)**
- 7–19 世纪约 36 万+人物(持续增长),历史人物库的世界级标杆。
- **用的是关系型数据库**(可下载 SQLite / 在线查询),不是图数据库:人物主档(名/字/号/生卒/籍贯/科第/任职)+ **亲属关系表 + 社会关系表**(两类关系分开建表)。
- 启示:人物主档是表格型数据,关系型最合适;连 36 万人的巨库都没把人物主档放进图库。

**2. 明朝历史知识图谱(aspxcor/Ming-Dynasty-Knowledge-Graph,34★)**
- 架构:MySQL 存实体属性表 + 关系表(事实源)→ **Neo4j 只做图谱可视化与查询**。
- 实体类型:人物/事件/地点/战争/机构/作品/时期;关系:父子/朋友/属于/影响等。

**3. 三国人物关系网络(baokun-l/sanguo-guanxitu,2025 新项目)**
- 与我们最像:维基爬取 → NLP/GLM 关系抽取 → **Neo4j 图谱 + NetworkX 社交网络分析**(中心性/社区/路径/派系)→ **Vue3 + D3 力导向图 + ECharts**,按势力着色;Neo4j 跑 Docker;前端可纯静态(JSON 内嵌)。
- 启示:"图谱页 = 力导向图 + 阵营着色 + 点人看关系"是成熟交互范式;小数据量下前端可直接吃 JSON。

**4. 红楼梦 KGQA(chizhu/KGQA_HLM,1339★)与三国 KGQA(BrambleXu,74★)**
- 最简模式:三元组 CSV → Neo4j 建图 → Flask 查询/问答。适合快速上线,但事实源直接落在图库里,复核/引文体系弱。

**共识与分歧**:
- 共识:①人物节点带属性(字/号/生卒/阵营);②关系用**受控词表**(不是自由文本);③可视化用力导向图、按阵营/势力着色;④人物→关系→关联事件可点击下钻。
- 分歧:事实源放关系库还是图库——**学术系(CBDB/明朝图谱)把事实源放关系库、图库只做查询层**;学生项目多为图库直建。前者可复核、可重建,后者快但易失控。

## 二、人物库方案(非关系库,按普通人物库做)

**结论:人物库继续用现有 PostgreSQL `pub.people`,做增强,不引入新存储**(与 CBDB 的选择一致)。

现状与问题:
- 442 人一人一行,全部有引文 ✓;但**别名字段缺失**(字/号/绰号只在 bio 正文里),检索"郝摇旗"搜不到"郝永忠"主档;
- 重名异人未处理(已知:高第两人被并成一行);
- 生卒缺 354/150。

增强四步:
1. **结构化别名**:加 `alias` 字段(jsonb 数组:字/号/别称/绰号,每项带类型),从已抽取 bio 和引文中回填;检索按 name + alias 联合匹配。
2. **人物合并治理**:复核已知问题(高第拆分为两人等);今后新抽取批次的人名进 stg 审核流时自动比对 alias/生卒,疑似同人走合并确认。
3. **生卒补齐**:《小腆纪传》(51.6 万字,人物列传为主)按传逐个抽取生卒/字号,经 WeKnora 检索辅助定位,补 `birth_year/death_year`(缺即缺,不猜)。
4. **人物卡数据**:现有导出已含 bio+引文,补 alias 后前端人物卡可直接展示"字XX,号XX"。

## 三、关系库方案(供选择)

现状:481 条关系已在 PG `pub.relations`,词表 13 类已成形:
`同盟145 / 敌对115 / 君臣104 / 同僚44 / 反目38 / 父子11 / 兄弟7 / 荐举5 / 叔侄3 / 师生3 / 舅甥3 / 夫妻2 / 姻亲1`。

三个方向:

### 方向 A(推荐):PG 唯一事实源 + Neo4j 只读图查询层
- 关系的**增删改、引文、审核全部留在 PG**(沿用现有 citations 体系);Neo4j 每次 export 后从 CSV **全量重建**,随时可删可重来,不存在双写一致性负担。
- 同步管道:export 时多产出两个文件 `graph/persons.csv` + `graph/relations.csv` → `neo4j-admin import`(秒级)。
- Neo4j 承担三件事:
  1. **关系路径查询**(Cypher 最短路径:"孙可望和李定国之间隔了几个人、经过谁"——这正是"交叉映照"后最有价值的问题);
  2. **图算法**(GDS 插件:PageRank/中心性找各阵营核心人物、社区发现自动聚类派系);
  3. **前端图谱数据源**(nodes+links JSON)。
- 前端:Next.js 加"人物图谱"页,D3 力导向图,按阵营着色(复用地图 faction 色),点人 → 人物卡+关系列表+关联事件。
- 与明朝图谱、三国关系网络同构,是开源界验证过的标准做法。

### 方向 B:关系直接建在 Neo4j(图库即关系库)
- 红楼梦 KGQA 模式,起步最快;但引文/审核/跨书合并逻辑都在 PG,事实源分裂成两套,以后每次抽取都要双写同步。**不推荐**(数据会越积越多,后期迁移成本高)。

### 方向 C:不引入 Neo4j,纯 PG + 前端直渲染
- 442 节点 / 481 边的规模,PG 递归 CTE 就能算路径,导出 JSON 给 D3 画力导向图,零新增容器。
- 代价:图算法(中心性/社区)要自己写或放弃;"关系链"查询的开发效率低于 Cypher。
- 适合"想先看效果、暂不加组件"的选择。**注意:此前已确认过 Docker Neo4j(~600MB)方案,若选 C 则作废该项。**

> 我的建议:**A**。理由:事实源唯一可复核(符合本项目引文至上原则);Neo4j 的 Cypher/GDS 对"关系链、派系分析"开发效率高;同步是单向一次性重建,维护成本≈0。若你想先轻量跑起来,C 也完全够用——图谱页本身两边一样,只是底层查询实现不同。
